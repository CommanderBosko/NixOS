# Improve System — Gotchas

Load this when a run looks anomalous: `fewer-permission-prompts` writes something odd, a "nothing to act on" verdict feels too easy, or a run claims to have finished without visible proof of Step 5.

- **`fewer-permission-prompts` (Step 2, item 6) has emitted invalid `settings.json`.** Observed across past sessions: it wrote permission entries with empty parentheses (e.g. `Bash()`), which fail Claude Code settings validation (`permissions.deny.N: Empty parentheses`), and it shelled out to `jq`/`python3` that returned `command not found` on this host. When orchestrating this step, auto-apply only concrete non-empty `permissions.allow` strings, drop any empty-paren entry before writing, and don't assume `jq` is on PATH.
- **A "nothing to act on" verdict must be earned by actually checking the logs, not inferred from context.** Asked in passing whether a pass was worth running, a prior response guessed "session was small, no friction" purely from what was still visible in the conversation, without invoking `skill-upgrade`'s transcript-grep step (`~/.claude/projects/<slug>/*.jsonl`) — it read as a real assessment but wasn't one. A "no work needed" conclusion is a perfectly fine outcome, but it must always follow from actually running that check first — never state a verdict, even offhand, as if the check happened when it didn't.
- **"Closing this tracking issue" is not proof Step 5 ran** (observed 2026-09-13, PR #23's run): the tracking-issue log went straight from the Step 3 consolidated-report comment to "Run complete. Closing this tracking issue," skipping Step 5's report-file write and `send-results` handoff entirely — no `~/.claude/improve-system/report-<ts>.md` for that date, no Discord post. Posting the consolidated report as an issue comment satisfies Step 3, not Step 5; they're separate steps with separate outputs. Before posting a "run complete" / closing comment, verify Step 5 actually produced its artifact — check that `~/.claude/improve-system/report-<ts>.md` exists for *this run's* timestamp and that the `send-results` handoff was actually invoked (not just planned) — rather than inferring it happened because the rest of the run went cleanly.
- **Implementing skill-audit's approved fixes hit a stale-content `Edit` failure** (observed 2026-09-16): after mining `skill-audit`'s `references/gotchas.md` early in the run to plan a fix, the actual `Edit` call later in the same run built `old_string` from that earlier read instead of the file's live content, and errored `String to replace not found in file` — the file's real structure (line breaks between adjacent bullets) didn't match what was held in memory from several steps back. This is the same class of bug already documented for `session-closer` (STEP 5's README edit) and guarded against in `skill-upgrade`'s own Step 4 routing logic: a long orchestration run holds file content in context far longer than a single-purpose skill does, so the staleness window is wider. Before any `Edit` this skill makes directly (not through a sub-skill) against a file read earlier in the same run — especially `references/gotchas.md` files a sub-skill's report told you to fix — `Read` it fresh immediately beforehand rather than reusing content from an earlier turn.
